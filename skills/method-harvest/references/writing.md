# Skill 写法参考

> 主文件：[SKILL.md](../SKILL.md)。本文件只在真要动笔写 skill 时读。

## 模板

```markdown
---
name: skill-name
description: 用在 [具体触发条件、症状、用户会说的话]
---

# Skill Name

## Overview
这是什么，核心原则一句话。

## Quick Reference
扫读用的表或要点。

## Implementation
简单模式内联代码；重的指到文件。

## Common Mistakes
会出什么错，怎么修。
```

## 命名

主动语态、动词优先、gerund 形式：

- ✅ `condition-based-waiting` / `writing-skills` / `root-cause-tracing`
- ❌ `async-test-helpers` / `skill-usage` / `helper` / `utils`

只用字母、数字、连字符。无括号、无特殊字符。

## description 的生死线

**只写何时用，永不概括流程。** agent 会拿摘要当指令，然后跳过正文。

**一个分支写一次触发。** 同一件事的多种说法是同一个分支写了多遍，收成一个；真正不同的分支才各留一条。

description 里 agent 会去 grep 的东西：

- 报错原文：`ENOTEMPTY`、`Hook timed out`
- 症状：`flaky`、`卡住`、`装不上`
- 分支本身：`首装` / `升级` / `已装但坏了`——三个不同分支，各写一次
- 具体工具名、库名、文件类型

克制：能写 500 字符就别写 1024。`getting-started` 类的 < 150 词。

## 自由度

按任务的脆弱程度定详略：

| 任务性质 | 写法 |
|---|---|
| 多条路都行，靠判断 | 文字原则 |
| 有偏好模式，允许变体 | 带参数的模板 / 伪代码 |
| 易错、必须完全一致 | 精确脚本，警告不要改 |

窄桥有崖：给护栏和确切步骤。开阔草地：给方向和信任。

## 一个例子胜过五个

选最相关的语言，写完整可运行、带注释解释为什么、来自真实场景。

不要：五种语言各一份、填空模板、编造的示例。agent 很会移植，一个好例子就够。

## 压力场景测试

纪律型 skill（禁令/规则）要这样验：

1. **写 3 个以上的压力场景**，叠加多种压力（时间 + 沉没成本 + 权威 + 疲惫）
2. **先不带 skill 跑**，逐字记下 agent 怎么违规、用了什么合理化借口
3. **写 skill**，只针对这些具体的借口
4. **带上 skill 再跑**，看是否合规
5. **发现新借口就补一条反制**，重复直到打不穿

技巧型 skill 验「能不能套用到新场景」；参考型验「能不能找到并正确使用」。

## 常见的逃测试借口

| 借口 | 现实 |
|---|---|
| "内容很清楚" | 对你清楚 ≠ 对其他 agent 清楚 |
| "这只是参考文档" | 参考也会漏、也会写不清 |
| "测试太小题大做" | 没测过的 skill 一定有问题 |
| "有问题再测" | 出问题 = agent 用不了，那时已上线 |
| "我很确定它没问题" | 过度自信保证出问题 |

## token 预算

每次会话只有 name + description 常驻；SKILL.md 只在触发时读。

但触发之后，它读的每个 token 都在跟对话历史抢地方：

- 默认假设 **agent 已经够聪明**
- 每一段都问：agent 真的需要这个解释吗？它不知道这个吗？这段值不值这些 token？

压缩手法：把细节推到 `--help`；交叉引用别的 skill 而不复述；砍掉同一模式的第二个例子。

## 别写时间敏感内容

```markdown
# ✗ 会过期
2026-08 之前用旧 API，之后用新的。

# ✓ 用「旧模式」小节装历史
## 当前做法
用 v2 端点。

## 旧模式
<details><summary>v1（2026-08 弃用）</summary>
...</details>
```

## 交叉引用

标记用 **REQUIRED SUB-SKILL**，格式：

```markdown
**REQUIRED SUB-SKILL**：<什么时候必须先读> `<skill-name>`
```

不要写 `@skills/xxx/SKILL.md` —— `@` 会立刻强制加载，白烧上下文。
