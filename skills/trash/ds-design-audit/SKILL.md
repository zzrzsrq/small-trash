# ds-design-audit

从屏幕上看到的东西打分，修最糟的几处，再拿证据说明修好了。审查基于渲染出的画面。

## 步骤

1. 找到目标文件或 URL，渲染出来；渲染不出来就报告并停手。
2. 在约 1440px 和 390px 两个宽度截图：首屏和整页；能拿到 hover、focus、空态、加载、错误态就一并截。没有能设视口的渲染器时，用桌面截图工具把窗口宽度拉到这两档再截，并在报告里注明"截的是窗口宽度，不是视口宽度"。
3. 读目标代码：tokens、字体、颜色、focus 样式、媒体查询、文案。
4. 每个维度打 1–5 分，每分给一行证据（屏幕上看到的，或某一行代码）：
   - 层级：3 秒内能看出主信息和主操作，只有一个焦点。
   - 字体：配对是有意的，字级成阶梯，行长和行高合适。
   - 颜色：一个主色一个强调色，颜色来自 token 而不是散落的 hex，渐变承载功能而非纯装饰。
   - 间距：间距按比例走，节奏一致，移动端对齐正确。
   - 状态：hover、focus、空、加载、错误、超长内容都有。
   - 可访问性：对比度 ≥ 4.5:1，focus 环可见，输入有 label，触控目标 44px，尊重 reduced motion。
   - 文案：产品特有的，无套话和占位数据。
5. 记下看到的"模板味默认件"：紫蓝渐变、标题用系统默认字体、拿 emoji 当图标、居中 hero 配三张同款卡片、到处玻璃拟态、灰底灰字、通用文案。
6. 按对用户的影响给修法排序：坏掉的可用性和不清的主操作在前，装饰在后。每条写清文件、改动、能提到几分。
7. 落地前 3–5 个，统一修在 token 或共享组件里。保住产品原本的身份、内容和行为。
8. 同宽度、同状态重新截图，重新打分，前后并排。
9. 还有维度 ≤ 2 分、或还有模板味默认件，就再做一轮 6–8。最多两轮。

## 什么时候停

- 两轮做完，或每个维度都 ≥ 3 分且没有模板味默认件。
- 报告里有前后分数、证据、已修的修法、以及没修的和为什么。

## 规则

- 每分都要有证据；看不到的维度标"未检查"并写原因。
- 事实性文案、价格、承诺、功能行为：要改先问。
- 需求本身就要那个风格，那不算缺陷。
- 需要整页重做交给 frontend-design。
