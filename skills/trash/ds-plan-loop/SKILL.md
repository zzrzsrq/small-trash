# ds-plan-loop

先规划，再一步一验地做。规划全靠记忆写，就是漏步骤的根源。

## 步骤

1. **复述目标**，一句话。列出预计会碰的文件和命令；规划前先读这些文件。
2. **写编号计划**。每步只做一件事，配一个**能被命令或观察确认的验收检查**，例如「`npm test -- auth` 通过」「`GET /health` 返回 200」。每步小到能在一个 diff 里验完。
3. **把计划写进文件**（`PLAN.md`；已有运行记录文件就写进去），让后续步骤和将来的新会话能读到。
4. **换一个视角批一次**。只重读「目标 + 计划」，当成没写过它的人来审，回答三个问题：
   - 缺了哪一步（初始化、迁移、配置、测试、清理）？
   - 哪个假设还没对着代码或文档核过？
   - 有没有更少步骤走到同一目标的路？
   有子代理就丢给子代理批，没有就隔一段再读。
5. **改计划**。每条有风险的假设当场核（读代码、跑命令）。
6. **只做第 1 步**。跑它的验收检查，读真实输出。检查不过 → 转 `ds-verify-loop`。
7. **在计划文件里标记完成**，连同证据（命令 + 结果），再进下一步。
8. **某一步证明计划错了**：停下来改剩下的步骤。

## 什么时候停

- 每一步都标了完成、检查都过，并回头整体验一遍原始目标仍然成立。
- 批评做了 2 轮。第 3 轮几乎不会发现新东西，直接执行。
- 某一步连续两次检查不过 → 转 `ds-verify-loop` 的「卡住了」段。

## 规则

- 每步都要有可运行的检查。「看起来对」不是检查。
- 一步一个 diff。
- 只保留目标需要的步骤。
- 计划保持 3–10 步。更大的活拆成几份计划。
