# ds-verify-loop

用真实检查证明改动有效。

## 步骤

1. 改代码前先选定检查命令：能证明这次改动的最窄的真实命令（单个测试文件、typecheck、build、带一个请求跑起来），写下来。
2. 能跑就先跑一遍，拿到基线：本来是过的、本来是挂的、还是因为别的原因跑不起来。
3. 做能满足这个检查的最小改动。
4. 跑同一条命令。读完整报错：第一条错误、文件和行号、栈里属于你代码的那一帧。
5. 用一句话说出根因。说不出来就加一行 print 或读失败的那段代码，再跑。
6. 修根因。为测试里那一个输入加特例不算修复。
7. 再跑同一条命令。这算一轮。
8. 窄检查通过后把宽检查跑一次（全量测试、build 或 lint），看有没有崩到别处。
9. 把最后通过的输出（命令 + 末尾几行）贴进回复；写进已有的运行记录文件（PROGRESS.md 之类）。

## 什么时候停

- 检查通过并贴了输出才算；只说"好了"不算。
- 5 轮还没过：停手，报最后那条错误，转下方「卡住了」。
- 同一条错误在两次不同修法后重复出现：立刻停。

## 后台脚本与守护进程

宣布这类脚本可用的标准：真实跑一次 + 等一个完整周期后复查。

- 用真实解释器执行脚本，确认它产生可观察的存活证据：进程在、日志有心跳、完成过一次循环。静态语法检查会漏——Windows PowerShell 5.1 会因脚本里的中文注释解析失败，而 `Parser.ParseFile()` 放行。
- 守护脚本写纯 ASCII，中文说明放进随附的 .md。
- 活着 = 等超过检查周期后进程仍在、日志有新的心跳行。

## 规则

- 让检查变绿靠真修复；删测试、跳过断言、放宽类型、关 lint 都不算。测试本身错了，说清理由再问。
- 只 mock 依赖，被测对象保持真实；整个 mock 掉测到的是别的东西，不算验证。
- 每一轮真跑命令。
- 一轮只改一处，这样你知道是什么修好的。
- 没有检查存在，就先写一个「不改代码就会挂」的最小检查，再进循环。

## 卡住了

同一条错误出现两次后别再试第三种变体。写下历次尝试各自改了什么、结果如何，写出这些尝试共享的那个假设（"跑的是这个文件""配置加载了""这函数收到的是字符串"），用最便宜的方法直接验证它（一行 print、grep 真实调用点、跑 `--version`），贴出结果。假设塌了，真问题就在那里；假设成立，就换机制而不是换参数。清掉失败尝试留下的残渣（`git stash` 或 `git checkout --`），只带新方案回去。
